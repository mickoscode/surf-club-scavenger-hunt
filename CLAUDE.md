# CLAUDE.md

Website for the Sorrento SLS Youth Scavenger Hunt 2026/27: a static site (`web/`) in a private S3 bucket behind CloudFront, Terraform in `terraform/`, GitHub Actions for CI/CD. Same AWS account as `surf-club-signin` (account `722937635825`, `ap-southeast-2`). The site runs the scavenger hunt game (rules: `docs/requirements.md`). See `README.md` for layout and `docs/setup.md` for one-time setup.

## Running a game

`docs/runbook.md` (what the admin does, in order, and what to do when something goes wrong) and `docs/rehearsal-checklist.md` (the manual dress rehearsal on real phones) are the operating manual: keep them in step with the pages and the admin controls. `tests/browser/full-game.test.js` is the automated rehearsal of a whole game; when you change how a game runs, run it.

## Frontend

- Pages are plain ES modules in `web/js/` (no framework, no bundler; `web/js/package.json` marks them as modules for Node and is not deployed). Logic that must agree with the server (phase, score format) lives in small pure modules (`time.js`, `format.js`) and `tests/unit/frontend.test.js` checks it against the server code. Team names and any other user text go on the page with `textContent`, never `innerHTML`.
- Pages find elements by `data-testid` and expose state as `data-*` attributes (`data-phase`, `data-seconds`, `data-team-number`, `data-score`): tests read those, never wording. `/` is only a redirect page to `/view/`.
- The instructions on `/play/` are `docs/player-instructions.md`, rendered into the page at build time by `scripts/render-instructions.js` (a `<details>` element: closed by default, the summary "Instructions (tap to show/hide)" is fixed by the requirements). Edit the Markdown, not the page.
- Zones on `/play/` (`web/js/zones.js`): tiles with map thumbnails, one panel per zone (opened with `#zone-1` in the address, so Back and reload work), one form per question and one for the photo, and a full-size map view. Each form can be submitted once; it is marked done only after the server confirms, then shows only "Done": never what was typed, never right or wrong (tests check). Number fields keep only digits (`web/js/answer-input.js`). `zones.render()` rebuilds only when the zones change, so a refresh never wipes a half-typed answer.
- Map images are build output: `scripts/build-maps.js` converts the PNGs named in `docs/game-questions.json` to `dist/maps/<mapId>.webp` and `<mapId>-thumb.webp` (`sharp`; a unit test limits their size for mobile data). `mapId` is one function in `api/lib/gamedata.js`, used by both the API and the build.
- Admin pages (`/game-config/`: config, teams, download and delete player data; `/game-score/`: score photos): behind the admin passcode (`web/js/admin-auth.js`: each page shows only a login box until the passcode is entered, handles log out and the 12-hour session ending while open, and skips its refreshes while locked; the pages stay ordinary public files, the admin API is what is protected), marked noindex in the page and by CloudFront, and not linked from any public page. They refresh every 5 s but update in place, so what the admin has chosen but not applied is never wiped. Team removal needs a confirm; deleting player data needs the download link clicked and the word typed, and is refused by the server while the game is active. The scoring page identifies a team by hidden form fields (team number and zone), never by anything typed, and Apply is only enabled when scoring is open and the choice differs from what is recorded.
- WhatsApp group link: an optional field in the game configuration, validated and normalised by `api/lib/whatsapp.js` (only `https://chat.whatsapp.com/<code>`), given ONLY to a team with a session through `/api/me` (a test scans every public response for it). `web/js/whatsapp.js` links every mention of the word in the photo challenges, the instructions and the scoring help, and refuses any other address on the page too. The Photo sent to WhatsApp button is an action, not a link, and must stay one.
- Layout rules are tested by measuring a real browser (`tests/browser/layout.test.js`), not by wording: status text and countdown share a line (a flex row with the same classes as before), the play page's team number and name share a line and differ in size and colour, and the view page shows the team's name only in its scoreboard row.
- Final results in the pages: the scoreboard heading (`web/view`), the Results button replacing Play (`me-area.js`: from the moment the game is over, published or not, decided in the browser from the server clock), the results link on `/play/`, the publish form on `/game-config/` and the read-only lock on `/game-score/` all follow the published flag. `/results/` (`web/js/results-page.js`, wording and medals in `results-format.js`, tested in Node) shows a team its place and breakdown ONLY when published and it has a session; a viewer sees only the link back. Everything the server sends is text on the page (a team's answers are user input). The smoke test checks the results route sends no answers to a visitor with no team.
- The join area on `/view/` (`web/js/me-area.js`) is only rebuilt when what it shows changes, so a scoreboard refresh never wipes a half-typed team name; a test guards that. `/play/` sends anyone without a team back to `/view/`. Browser tests sign a team in by setting the session cookie (`signIn` in `tests/browser/helpers.js`) and turn the browser's HTTP cache off, because the API's 3-second cache headers are obeyed by Chromium too.
- `?refresh=500` shortens the scoreboard refresh (the browser tests use it).
- Bootstrap 5 (npm dependency, pinned) is copied into `dist/vendor/bootstrap/` by `scripts/build.sh`; it is not committed. `dist/` is the exact bucket contents and is gitignored.
- Mobile first: base styles are for phones, `@media (min-width: ...)` only enlarges. Prefer Bootstrap utilities and grid before adding CSS to `web/css/site.css`.
- The CSP (`terraform/cloudfront.tf`, `local.content_security_policy`) allows only same-origin scripts, styles, images (plus `data:`), fonts and connections. No inline `<script>`/`<style>`/`style=""`/`on*=` handlers and no CDN or external URLs. If a feature needs more (an API, an image host), widen the CSP deliberately in the same PR and update `tests/build.test.js` if its assumptions change.
- Use site-absolute paths (`/css/site.css`), because `404.html` is served from any URL.
- Static assets are synced with `Cache-Control: no-cache` and CloudFront is invalidated on each deploy, so there is no filename hashing.

## Backend

- `api/` is the backend, plain CommonJS with no runtime dependencies (the AWS SDK comes with the Lambda runtime). `api/lib/` holds pure game logic: nothing there touches AWS, the clock (always passed in) or the network, so it is unit tested directly in `tests/unit/`. `api/store/` is the data layer: one `store` interface with `memory.js` (local development, handler and browser tests) and `dynamo.js` (production; one table, a team's whole state is one item so "submit once + add to score" is one atomic conditional update). `tests/api/contract.js` is the specification both must pass: it runs against the memory store everywhere and against DynamoDB Local in CI (`API tests`). Change behaviour in the contract first. `api/app/app.js` holds the routes (public and admin roles, deployed as two Lambda functions via `api/handlers/`), `api/app/lambda.js` adapts API Gateway events; the API is documented in `docs/api.md` (keep it in step with the routes). The app tests (`tests/api/app-*.test.js`) use the memory store and a fake clock, and check status/error codes, never wording. They include the leak tests: no public response may contain an official answer, a submitted answer or a team's secret id.
- Final results: the admin publishes them (only once the game is over, with an "all scores applied" confirmation; unscored photos count as 0%) and can return to provisional. While published, scoring is locked (409 `results-published`); deleting player data or saving the configuration returns to provisional. `GET /api/results` sends a team's breakdown (`api/lib/results.js`) ONLY when published AND the caller has a team session; before that it sends nothing about answers (tests scan for leaks). The published flag is one item (`META/RESULTS`) in the store, with the same contract tests as everything else. Places are shared by equal scores.
- Admin passcode (`api/lib/passcode.js`): only a scrypt HASH is stored (HCP sensitive variable `admin_passcode_hash` -> the admin function's `ADMIN_PASSCODE_HASH`; make it with `scripts/admin-passcode.js` on the admin's own computer). Login sets a 12-hour signed session cookie (`hunt_admin`, `Path=/api/admin`) signed with a key from the hash, so a new passcode ends every session. Every admin route except `session`, `login` and `logout` needs it (401 `not-authenticated`); 10 failed logins per 5-minute window across everybody locks logins for the rest of the window (counted in the store). Empty hash = admin open (rollout); an invalid hash = admin locked, never open. New admin routes are gated automatically; keep the plaintext passcode out of the repo, logs, tests (they use a cheap hash) and responses.
- Events (`api/lib/events.js`, files in `api/store/blobs.js`: in-memory for tests, S3 in AWS): games prepared in the private events bucket, written only through the admin routes. The live game never reads the bucket: `PUT /api/admin/config` with an `event` copies the event into the game's table and its maps into the site's `event-maps/<activation>/` (the deploy sync excludes that folder). Event names, image types (by content), sizes and event counts are checked in one place (`events.js`); routes must stay 400 (never 404/403) for unknown events. `tests/api/routes.test.js` keeps the app's routes and `terraform/api-gateway.tf` identical.
- The server decides everything (timing, answer checking, scoring); official answers and submitted answers never go to the browser. Known and accepted: the repo is public, so the answers are readable on GitHub (see `docs/requirements.md`); the admin is protected by the passcode. Rules are in `docs/requirements.md`, and the code comments point to the relevant section.

## Infrastructure

- HCP Terraform org `mickoscode`, workspace `surf-club-scavenger-hunt` (remote execution; state and AWS credentials live there). Secrets are workspace variables, never in tfvars or the repo (the repo may be public).
- The bucket is private, readable only by this CloudFront distribution (OAC). The deploy role (`scavenger-hunt-deploy-role`) trusts only this repo's `main` branch (matched on the immutable OIDC subject `github_oidc_subject_prefix`, not the repo name) via the account's existing GitHub OIDC provider, which is owned by `surf-club-signin` and only looked up here.
- API: CloudFront sends `/api/*` to an API Gateway HTTP API (two Lambda functions, one DynamoDB table; `terraform/lambda.tf`, `api-gateway.tf`, `dynamodb.tf`). Lambda code is NOT managed by Terraform (placeholder + `ignore_changes`): the deploy workflow pushes it. Only the routes listed in `api-gateway.tf` exist; add a route there when you add one in `api/app/app.js`.
- CloudFront custom error pages apply to every behaviour, so the API must never answer 403/404 for its own errors (a test enforces it).
- Only `/api/game` and `/api/scoreboard` are cached (3 s, nothing in the cache key); everything else under `/api/*` is uncached with the session cookie passed through. Never point a personal route at the shared cache policy.
- `terraform/rewrite.js` (CloudFront Function) serves `/view/` as `/view/index.html` and redirects `/view` to `/view/`; `tests/unit/rewrite.test.js` runs it.
- Trivy accepted findings are in `terraform/.trivyignore.yaml`, each with a reason.
- `domain_name` is empty until a custom domain is chosen (see `docs/setup.md`).

## CI/CD

- `web-pr.yml` (`Validate site`, `API tests`, `Browser tests`, `Game data`) and `terraform-pr.yml` (validate, security scan, plan comment) run on PRs and are skipped, not absent, when their folders are unchanged, so they can be required checks.
- Load test (`scripts/loadtest/`, run only by hand from `.github/workflows/load-test.yml`, in the `deploy-prod` concurrency group): it must stay safe for the live site: caps (300 teams, 1,500 spectators, 900 s), refuses with any real team present, never changes the game configuration, removes only teams named `loadtest-*`, uses `ADMIN_PASSCODE` (GitHub secret) only for that. Keep the generator's request pattern the same as the real pages' (5 s refresh) when pages change; its tests are in `npm test`.
- Merging to `main` deploys: `deploy.yml` for the backend and the frontend (needs repo variables `CF_DISTRIBUTION_ID` and `SITE_URL`). The backend zip is `build/backend` (`scripts/package-backend.sh`: only `api/app`, `handlers`, `lib`, `store` plus a copy of `docs/game-questions.json`), and `tests/api/package.test.js` runs it in isolation, so anything the Lambda needs must live under `api/`. After the deploy, `scripts/smoke-test.js` checks the live site (read-only, retried); add a check there when you add something that could fail silently in production, `terraform-apply.yml` for `terraform/` (manual approval in the `terraform-production` environment). `terraform-drift.yml` checks weekly.
- Actions are pinned to commit SHAs with a version comment; Dependabot bumps them weekly.

## Working conventions

- Raise PRs with `gh` from a feature branch and commit only the files you changed (explicit `git add` paths). The owner reviews and merges every PR and handles GitHub settings, HCP/AWS settings and Terraform applies.
- Tests only where a regression would really hurt. No trivia or "guard" tests, and nothing that depends on wording: tests use their own fixtures, never `docs/game-questions.json`, the instructions or page copy. Find elements by `data-testid`, not by text. Layout: `tests/unit/` and `tests/api/` (both run by `npm test`; the store contract also runs against DynamoDB Local in CI) and `tests/browser/` (`npm run test:browser`: Playwright and Chromium against the real pages and API code, served with the CSP read from `terraform/cloudfront.tf`). Browser tests skip locally if Chromium is missing and fail in CI (`REQUIRE_BROWSER=1`). When you change a page, mutate it once to check the test really fails (e.g. swap `textContent` for `innerHTML`).
- `scripts/validate-game-data.js` is the only thing that reads the real `docs/game-questions.json`, and it checks structure only (format in `docs/requirements.md`). It runs in CI as the `Game data` check.
- Keep it simple: this site is deliberately much smaller than `surf-club-signin`.
